3) Technical guardrails (platform‑agnostic, z/Linux‑friendly)
A. Data boundaries & egress

Force AI traffic through a gatekeeper / proxy that: (1) enforces allow‑listed models; (2) strips sensitive data; (3) attaches policy context (tenant, data tags, purpose).
For zLinux/mainframe‑adjacent workloads: keep inference endpoints on dedicated VLANs; mutual‑TLS with FIPS 140‑3 crypto; forward journald/syslog to SIEM with tamper‑evidence; model artifact pulls only from curated repos (you already do this for Falcon RPMs—use the same Artifactory pattern).
Maintain a Model Registry (name, version, license, training data lineage, eval scores, owners, risks).

B. Identity, secrets, and “least agency”

Short‑lived tokens for tools/plugins; scoped so LLM agents cannot list or escalate capabilities.
Apply “excessive agency” controls (no shell, no arbitrary network, no prod write ops) unless explicitly approved with compensating safeguards. (OWASP LLM Top 10) [owasp.org]

C. Prompt I/O hygiene

Treat retrieved content as untrusted; separate “instructions” from “data,” validate outputs before tool execution, and implement deny‑patterns for common injections. (OWASP LLM01/Output Handling) [owasp.org]

D. Telemetry & audit

Minimum events: model ID/version, tool invocations, data tags, policy decisions (allowed/blocked), redaction actions, evaluator scores, and user identity. Map to AU‑2/AU‑3; retain per your regulatory clocks. [csrc.nist.gov]

E. TEVV & red‑teaming

Pre‑prod adversarial testing per EO 14110/NIST AI RMF; include jailbreaks, data leakage, prompt‑injection, RAG poisoning, and cost‑DoS scenarios (unbounded consumption). [bidenwhite...chives.gov], [nist.gov]

Core idea: treat models, prompts/agents, RAG pipelines, vector DBs, tool bindings, datasets, and evaluation configs as configuration items (CIs). Apply configuration management and auditability just like you would to OS baselines and application stacks.


CM‑6 – Configuration Settings / Hardening
What it means for AI: define hardened baselines for each CI:

Models: approved base model list; allowed quantization levels; permitted fine‑tune sources; cryptographic hash; approved serving parameters (context length, temperature, top‑k/p).
Prompts/Agents: system prompt templates are versioned, read‑only in prod; tool lists are least‑privilege; no generic code execution by default.
Vector DBs / RAG: schema is locked; ingest pipelines are curated; only signed CI/CD can write to prod embeddings; indexing parameters (HNSW/IVF, ef_search, filters) are baseline‑controlled.
Gateways: model allow‑lists; data redaction policies; egress destinations; rate limits and cost budgets.
The control outcome is the same as traditional CM‑6: baseline + ownership + enforcement + drift detection. [soma.larc.nasa.gov]



CM‑3 / CM‑4 – Configuration Change Control & Monitoring
Ensure change approval for model version bumps, prompt template diffs, and index rebuilds; monitor drift in embeddings, prompts, and model parameters with signed releases and reproducible builds. [soma.larc.nasa.gov]


CM‑2 – Baseline Configuration
Publish minimum secure configs for inference services (TLS/mTLS, logging on, no interactive shells), vector stores (authN/authZ, encryption at rest), and gateways (PII redaction, domain allow‑lists). [soma.larc.nasa.gov]


AU‑2 / AU‑3 – Event Logging & Content of Audit Records
Log who/what/when/why for each AI action: modelID/version, prompt hash, retrieved document IDs, tool invocations, policy decisions (allow/deny/redact), output disposition. Include timestamps, subject identity, success/failure, and object references (CI identifiers). [csrc.nist.gov]


AC‑x / IA‑x – Access Control & Identification/Authentication
RBAC/ABAC over artifacts and runtime actions (e.g., Curator can stage embeddings but not publish; Model Owner can approve a version but cannot alter cluster infra). Enforce short‑lived, scoped credentials for tools and plugins. [soma.larc.nasa.gov]


RA / PM / SA – Risk, Program Mgmt, System & Services Acquisition
Use NIST AI RMF “Govern/Map/Measure/Manage” to frame risk, TEVV, and lifecycle, and align acquisition/vendor intake to require model cards, safety tests, and SBOMs. [nist.gov]

Add playbooks for prompt‑injection, RAG poisoning, unbounded consumption (cost DoS), and model exfil/leakage (OWASP GenAI Top 10 categories). [owasp.org]

2. How Global AI Regulations Overlap — and Where They Diverge
Global AI regulatory frameworks fall into three broad categories:

Principle‑based frameworks (NIST AI RMF, ISO/IEC 42001, ISO/IEC 23894) — voluntary, risk‑based, lifecycle‑focused
Binding regulatory law (EU AI Act) — highly prescriptive, enforceable obligations
Executive‑level directives (US EO 14110) — not laws, but mandates for federal agencies and strong signals to private sector

Despite huge differences in enforcement, all share a series of common governance themes — and then diverge sharply on requirements, documentation burden, conformity, and penalties.

🌍 PART A — THE COMMON GLOBAL CORE (Where they overlap)
Below are the global points of convergence that appear consistently across the EU AI Act, ISO, and NIST frameworks.

✅ 1) Risk Management Across the AI Lifecycle
Every major global framework emphasizes a structured, multi‑phase risk evaluation and mitigation lifecycle.

NIST AI RMF explicitly defines Govern → Map → Measure → Manage as a comprehensive lifecycle. [nist.gov]
ISO/IEC 42001 establishes an AI Management System (AIMS) requiring planning, operations, performance evaluation, internal audits, and continuous improvement. [iso.org]
ISO/IEC 23894 is specifically about AI risk management, mapping risks across the AI lifecycle. [iso.org]
EU AI Act requires documented risk management systems for high‑risk AI, including testing, monitoring, and mitigation plans. [artificial...enceact.eu]

Overlap Summary:
Everyone agrees AI governance must be risk‑based, documented, and lifecycle‑driven.

✅ 2) Data Governance & Data Quality Controls
Every major framework places obligations around data used for training, evaluating, and operating AI systems.

EU AI Act mandates strict data and data governance practices for high‑risk systems, ensuring data relevance, representativeness, and quality. [artificial...enceact.eu]
ISO/IEC 23894 highlights risks around data quality, bias, and contextual sensitivity. [iso.org]
NIST AI RMF includes data considerations in MAP and MEASURE functions as foundational. [nist.gov]

Overlap Summary:
All frameworks require data governance, bias mitigation, and data quality management.

✅ 3) Logging, Traceability, and Auditability
This is universally emphasized.

EU AI Act requires logging, record‑keeping, system logging, and technical documentation for high‑risk systems. [artificial...enceact.eu]
NIST SP 800‑53 (AU‑2, AU‑3) defines detailed requirements for the content and selection of audit logs. [csrc.nist.gov]
NIST AI RMF explicitly ties traceability to trustworthy AI outcomes. [nist.gov]
ISO/IEC 42001 requires documentation, measurement, and performance review of AI systems. [iso.org]

Overlap Summary:
Global consensus: AI requires extensive logs, telemetry, and traceability for safety, compliance, and forensics.

✅ 4) Human Oversight
All frameworks require mechanisms for meaningful human oversight.

EU AI Act mandates human oversight for high‑risk AI and defines detailed expectations for transparency and controllability. [artificial...enceact.eu]
NIST AI RMF references human‑AI interaction and responsible decision pipelines. [nist.gov]
ISO/IEC 42001 includes leadership, roles, responsibilities, and competency requirements. [iso.org]

Overlap Summary:
Humans must remain in the loop for consequential decisions.

✅ 5) Security, Robustness, and Adversarial Testing
Everyone agrees AI must be secure and resilient.

US EO 14110 requires red‑team testing for powerful AI models before release. [bidenwhite...chives.gov]
EU AI Act requires robustness and cybersecurity controls for high‑risk AI. [artificial...enceact.eu]
NIST AI RMF emphasizes robustness, safety, and resilience as core trustworthiness targets. [nist.gov]

Overlap Summary:
AI systems must undergo security testing, adversarial evaluation, and robustness validation.

4 — Threat Modeling for Unauthorized Configuration Changes
Unauthorized configuration modification is the #1 root cause of AI misbehavior in enterprise systems.
AI systems are unusually vulnerable because behavior = configuration, not just code.
This section defines:

The threat surfaces
Attack scenarios
Why they matter
Controls that mitigate them
Which framework(s) require them


✅ I. Core Premise: AI Behavior = Configuration
Traditional apps derive behavior from code.
AI systems derive behavior from:

Model artifacts (parameters, quantization, fine‑tunes)
Prompt templates & agent logic
Vector DB / embeddings corpus
Tool/plugin scopes & allowed actions
RAG retrieval rules
Gateway policies (redaction, egress, model allow‑lists)

Manipulating any one of these changes the system’s behavior without altering code — a direct compliance and safety risk.
This configuration‑centric risk is explicitly recognized in:

ISO/IEC 23894 (AI lifecycle risks including data/model modification) [iso.org]
OWASP GenAI Top 10 (prompt injection, supply chain, excessive agency, insecure output handling) [owasp.org]
NIST SP 800‑53 CM‑6 / CM‑3/4 (baseline configuration + change control requirements) [soma.larc.nasa.gov]
NIST AI RMF (“Measure/Manage” requires evaluation + monitoring of AI-specific risks) [nist.gov]


✅ II. Threat Surfaces for Unauthorized Configuration Changes
1. Model Artifact Manipulation
Threats

Replacing a model with an unapproved version
Inserting a tampered checkpoint into the model registry
Switching quantization or sampling configs to reduce safety

Why it’s dangerous
Changes the entire behavioral profile of the system — safety, accuracy, bias, hallucination rate.
Standards referencing risk

NIST SP 800‑53 CM‑6 / CM‑5: secure baseline + restrict modification. [soma.larc.nasa.gov]
EO 14110: requires safety testing before release of powerful AI. [bidenwhite...chives.gov]
ISO/IEC 42001: requires documented controls + integrity of AI assets. [iso.org]


2. Prompt Template / Agent Logic Tampering
Threats

Editing the system prompt to weaken guardrails
Inserting harmful logic in tool‑execution templates
Agent goal redefinition (“role swap attacks”)

Why it’s dangerous
Prompts define reasoning boundaries. Tampering bypasses safety constraints.
Referenced in

OWASP LLM01 Prompt Injection (direct/indirect) [owasp.org]
NIST AI RMF (trustworthiness requires documented, tested logic) [nist.gov]


3. Vector DB Poisoning (Embedding or Document Injection)
Threats

Writing malicious embeddings to prod
Modifying or deleting documents that inform RAG
Manipulating metadata filters (e.g., document classification tags)
Changing similarity index configs (HNSW/IVF parameters)

Why it’s dangerous
Vector databases determine what the LLM believes. Poisoning = controlled misinformation.
Referenced in

ISO 23894 (data-related risks & emergent behaviors) [iso.org]
OWASP Training Data Poisoning (LLMs & RAG systems) [owasp.org]
EU AI Act (high‑risk systems require documented data governance + integrity) [artificial...enceact.eu]


4. Tool / Plugin Scope Escalation
Threats

Expanding tool privileges (filesystem, network, code execution)
Exposing unrestricted APIs to the LLM
Assigning admin-level credentials to a generic agent

Why it’s dangerous
OWASP calls this “Excessive Agency” — the most destructive LLM vulnerability class.
LLMs with elevated capabilities can exfiltrate data, delete files, or take external actions.
Referenced in

OWASP Top 10 (LLM Excessive Agency, Insecure Plugin Design) [owasp.org]
NIST SP 800‑53 AC/IA (least privilege & identity control) [soma.larc.nasa.gov]


5. Gateway / Egress Policy Bypass
Threats

Sending sensitive data directly to public LLM APIs
Using unapproved API keys or endpoints
Bypassing redaction, provenance, or logging

Why it’s dangerous
Violates data governance & privacy laws — especially dangerous for medical, financial, and government workloads.
Referenced in

EU AI Act (Art.10) — data governance + quality obligations [artificial...enceact.eu]
EO 14110 — provenance + safety for powerful models [bidenwhite...chives.gov]
NIST AU‑2/3 — logs required for compliance evidence [csrc.nist.gov]


6. Retrieval Pipeline Manipulation
Threats

Changing RAG scoring functions (similarity thresholds, top‑K)
Altering document preprocessing logic
Switching embedding models silently

Why it’s dangerous
Changes semantic meaning, relevance, and factual grounding — invisible drift.
Referenced in

ISO/IEC 23894 (context sensitivity & drift) [iso.org]
NIST AI RMF Measure/Manage (continuous monitoring required) [nist.gov]


7. Safety Filter / Guardrail Bypass
Threats

Disabling toxicity or hallucination detectors
Reducing thresholds for output filtering
Altering rules for harmful content classification

Why it’s dangerous
Directly undermines compliance with safety standards, policy, and legal obligations.
Referenced in

EO 14110 (safety eval frameworks before use) [bidenwhite...chives.gov]
EU AI Act (accuracy, robustness, cybersecurity) [artificial...enceact.eu]


✅ III. Attack Scenarios
Here are concrete threats combining the above surfaces.
✅ Scenario 1 — Vector Store Poisoning
Attacker with curator access injects a single malicious document containing instructions that override system prompts (OWASP Indirect Prompt Injection).
LLM retrieves this during RAG and outputs harmful or incorrect actions.
 [owasp.org]
✅ Scenario 2 — Silent Model Swap
Ops team member swaps a fine‑tuned checkpoint for a different build without approval.
Changes bias, hallucination rate, or jailbreak resistance.
Violates CM‑6 and EU risk management requirements.
 [soma.larc.nasa.gov], [artificial...enceact.eu]
✅ Scenario 3 — Prompt Template Sabotage
Developer modifies the main system prompt to weaken safety responses.
This bypasses guardrails without touching code.
 [owasp.org]
✅ Scenario 4 — Gateway Egress Bypass
User configures a notebook to send prompts directly to public LLM endpoints, bypassing redaction and logging.
Violates EU AI Act data governance requirements and NIST audit rules.
 [artificial...enceact.eu], [csrc.nist.gov]
✅ Scenario 5 — Tool Scope Escalation
Agent is granted temporary OS shell access “for debugging,” never revoked.
LLM now can delete or exfiltrate data.
 [owasp.org]

How to Implement Signed CI/CD for Models, Prompts & Vector DB Artifacts
The core goals of signed CI/CD are:

Integrity — artifacts cannot be tampered with.
Provenance — you know who built what, when, and from which sources.
Enforcement — production only runs artifacts signed by an approved pipeline.
Auditability — every change is traceable with cryptographic evidence.

This makes the AI stack behave like a “high‑assurance supply chain.”
Below is the proven pattern used across high‑security environments.

✅ 1. Introduce a Cryptographic Trust Root (Key Management)
You need two types of keys:
A) Build‑Time Signing Key (private)

Lives inside the CI/CD runner (or better: a hardware module like HSM/KMS).
Used only for:
✅ signing model artifacts
✅ signing prompt/agent bundles
✅ signing vector ingestion manifests
✅ signing configuration baselines

B) Verification Key (public)

Distributed to inference servers, gateways, registries.
They verify signatures before allowing use.

Best practice

Keys must rotate.
Signing key must NEVER leave CI/CD.
Verification key can be widely distributed — safe to expose.


✅ 2. Define the “Artifact Types” That MUST Be Signed
You should treat every behavior‑defining component as a signable artifact:
Model artifacts

Base models, fine‑tunes, quantized builds, adapters (LoRA, QLoRA).
Tokenizers & vocabulary files.
Sampling parameter specs (temperature, top‑p, max‑tokens).

Prompt & agent logic bundles

System prompts
Tool definitions
Agent planning trees
Few‑shot examples

Bundle them into a versioned tarball → sign the tarball.
Vector DB artifacts

Embedding files (batch outputs)
Index files (e.g., HNSW/IVF indices)
Ingestion manifest (source IDs, metadata, classifiers)

Configuration baselines

RAG pipeline config
Gateway allow‑lists
Safety filter rules


✅ 3. Build → Test → Sign in CI/CD
Below is a typical pipeline structure:
pipeline:
  stages:
    - build
    - test
    - eval
    - sign
    - publish

✅ Build Stage

Package artifacts (model weights, prompt bundles, indexes).
Generate metadata:

model_id
version
git commit SHA
dependency hashes
training/eval inputs (if applicable)



✅ Test Stage

Unit tests (for agents/pipelines).
Schema checks (metadata validation).
Ensuring no disallowed dependencies.

✅ Eval Stage

Run TEVV (Testing, Evaluation, Verification & Validation):

Safety tests
Bias tests
Jailbreak resilience
RAG quality
Hallucination checks
Cost control simulations



✅ Sign Stage
signing_key = loadFromHSM()
signature = sign(artifact.tar.gz, signing_key)
write signature → artifact.sig


CI/CD stamps:

Date/time
Pipeline ID
Build runner identity
Git SHA



✅ Publish Stage

Push signed artifacts to your Model/Prompt Registry.
Push ingestion manifests + signed indexes to Vector Registry.
Emit logs to SIEM (promotion event).


✅ 4. Enforce Signature Verification at Deploy and at Runtime
Deployment enforcement
Inference servers, vector DB instances, and gateways must refuse:

unsigned artifacts
artifacts with mismatched signatures
artifacts signed by old/retired keys

Runtime enforcement

On startup: verify all artifacts.
Periodically: re‑validate signatures (e.g., every 8–12 hours).
On hot‑swap (model load, prompt change): verify again.

Drift detection
If a config file/hash deviates → refuse to start or trigger an alert.

✅ 5. Promotion to Production = Signed + Approved + Logged
A Promoter identity (machine account) executes the signed promotion job.
It must:

Publish only signed artifacts
Use a “promote-to-prod” CI job requiring:

Approvals from Model_Owner
Approvals from AIMS_Admin (for high‑risk)
Signature validation


Log an immutable entry:

who approved
who promoted
what artifact
what versions replaced
signature hash




✅ 6. Registry Enforcement
The registry will:

Reject unsigned uploads
Store signatures and metadata
Keep all versions (append‑only)
Serve artifacts to inference servers only if signature matches
Provide audit API for investigators

You now have a cryptographically provable chain of custody.

✅ 7. Zero Human Access to Production Writes

No engineer can “scp a model” into prod.
No one can “update a vector index” manually.
All writes must come only from the signed CI/CD promoter identity.

This eliminates 95% of configuration‑tampering risk.

✅ 8. Multi‑Environment Considerations
On‑Prem (zLinux, HPC, GovCloud)

Use HSM or internal KMS for signing keys.
Verification key baked into RPMs or loaded via secrets manager.

Private Cloud

Use cloud KMS signing keys.
Verification key distributed with IaC (Terraform/Ansible).

Public Cloud

Use managed signing services (AWS KMS, Azure KeyVault CERT, GCP KMS).
Verification key stored in secret manager.

Promote‑to‑Prod Flow for AI Artifacts
(Models, Prompts/Agents, Vector DB Indexes)
The promote‑to‑prod pipeline is the central safety backbone of an AI governance program.
Its purpose is to ensure:

Only approved, tested, signed, auditable artifacts reach production.
No one can “sneak” changes into AI behavior.
Every promotion is reproducible, reviewable, and reversible.

Below is the complete lifecycle.

✅ 1. Trigger: A Change Is Proposed
A new artifact enters the pipeline when:

A new model version is produced (base model, fine‑tune, quantization, adapter, tokenizer change).
A new prompt/agent template is proposed.
New RAG documents are curated and embeddings generated in staging.
A new vector index is built (HNSW/IVF/flat).
A change to safety filters or tool configuration is submitted.

At this stage, nothing is permitted anywhere near production.

✅ 2. Build Stage (Package the Artifact)
The CI/CD pipeline:

Packages the artifact into a standard bundle (e.g., model.tar, prompts.tar, index.hnsw.tar).
Computes hashes for files and dependency metadata.
Generates an artifact manifest (metadata including risk tier, owner, model ID, etc.).

This creates the immutable input for testing.

✅ 3. TEVV Phase (Testing, Evaluation, Verification & Validation)
TEVV is mandatory before promotion. It ensures the change is safe before reaching prod.
Includes:
✅ Safety & Robustness Testing

Jailbreak resistance tests
Harmful output check
Adversarial input tests
Prompt‑injection simulation
Output‑validation tests

✅ Bias/Fairness Testing

Evaluate bias metrics
Ensure no harmful drift compared to previous models

✅ Performance Testing

Latency benchmarks
Token/embedding accuracy
RAG relevance tests

✅ Cost & Abuse Testing

Recursive calls detection
"Unbounded consumption" (LLM DoS) tests
Prompt amplification checks

✅ Regression Testing

Behavior consistency checks
Validation against historical expected responses

Only if TEVV passes, the pipeline advances.

✅ 4. Risk Assessment + Human Approvals
After TEVV, two approvals are needed:
✅ Model_Owner Approval

Confirms behavior, quality, risks, and intended use.
Reviews TEVV results.
Ensures outputs align with business and risk expectations.

✅ AIMS_Admin Approval (for high‑risk AI)

Ensures change aligns with governance, safety, and regulatory posture.
Verifies documentation completeness (model card / AIIA).
Confirms compliance with internal and external frameworks.


✅ 5. Signing Stage (Cryptographic Integrity)
Once approvals are given:

The CI/CD pipeline signs the artifact using a private signing key stored in KMS/HSM.
A .sig file is produced.
Both the artifact and signature are stored in the Model/Prompt/Vector Registry.

This ensures:

No artifact can be modified after approval.
Only artifacts signed by CI/CD are eligible for promotion.
Production environments can cryptographically verify everything they run.


✅ 6. Promotion to Production (Executed by Promoter Identity)
This is the only step where anything touches production.
✅ The Promoter identity:

Is a machine/service account, not a human.
Has just enough privileges to publish to prod.
Only runs signed CI/CD promotion jobs.

✅ Promotion actions:

Upload model bundle → production model store
Upload prompt bundle → production config store
Publish vector index → production vector DB
Update model registry → set new version to “active”
Notify gateway → update allow‑lists, routing rules, feature flags

✅ All actions are automatically logged:

who approved
who promoted
what artifact
old vs. new version
hash/signature
time of deployment

These logs provide auditability and rollback certainty.

✅ 7. Runtime Verification
When the production inference service starts or loads a new model:

It verifies signatures using the verification key.
It verifies the artifact hash matches the registry.
It verifies the configuration matches the approved baseline.
It refuses to load unsigned or mismatched artifacts.
It emits telemetry showing signature check results.

This eliminates silent tampering.

✅ 8. Post‑Deployment Health Checks
Immediately after promotion:

Shadow testing or canary release compares old and new behavior.
Drift monitors ensure no unexpected output deviations.
Performance monitors check latency and correctness.

If anything deviates from acceptable thresholds, rollback triggers.

✅ 9. Rollback Capability
Every promotion must have a rollback plan:

Previous version kept available (“previous active version”).
Rolling back is just another promotion job — signed & logged.
Gateway routing switches back to stable model.
Vector DB index switch (if needed) is atomic (point to previous index).

Rollback is treated as a first‑class citizen, not an afterthought.

✅ 10. Post‑Market Monitoring
After production:

Ongoing drift detection
Safety monitoring
Usage analytics
Abuse/threat detection
Continuous retraining feedback loops
Incident alerts (prompt injection, RAG poisoning, unexpected autonomy)

This completes the end‑to‑end lifecycle.

✅ In Short — The Promote-to-Prod Flow Is:
Propose → Build → TEVV Tests → Approvals → Sign → Promote (CI/CD-only)
    → Runtime Verify → Canary/Shadow → Monitor → Rollback if required

Key principles:

Humans approve → Machines promote.
Nothing runs without signatures.
No direct human write access to production.
Behavior changes are fully traceable and reversible.
